# חוזה הפלט של לבנת אימונים — מוח המאמן ↔ מודול אדמין

**נקבע 2026-09-03** בין מודול האדמין ומודול מוח המאמן, ואושר על ידי בעל המוצר.
זה המסמך שמולו נבנה החיבור ב-22.1. אין בו כלום שרץ ב-22.0.

## מה 22.0 עושה, וזה כל מה שהיא עושה

`COACH_BUILD_MAY_SAVE = false` (ב-`admin.html`) — לבנה שחוזרת מהמאמן **מוצגת ולא
נשמרת**, והבדיקה קורית לפני קריאת השמירה בשני מסלולי התחקור. `ATHLETE_AI_BUILD_ENABLED`
נשאר `false`, כלומר סיום תחקור לא מבקש לבנה בכלל. החיבור בגרסה הזו הוא **בדיקת צינור**:
מוכיחים שהחבילה מגיעה ושתשובה חוזרת, והתשובה נזרקת.

הסיבה שהשמירה חסומה ולא רק "לא נלחצת": לבנה שנשמרת היום נכתבת לעולם המתאמנים הישן,
שהמסך שלו ירד עם טאב המאמן — תוכנית שאף אחד לא יכול לפתוח.

## מה המאמן מתחייב להחזיר

`<<<BLOCK_JSON ... BLOCK_JSON>>>` ובתוכו `weeks` — **בדיוק 4**.

```
week = { weekIndex, phase, theme, summaryLine, overview[7], days{} }
overview[i] = { day: "sun", label: "Sun", focus: "..." }     // כל 7 הימים, תמיד
days = { sun: { parts: [...] }, mon: {...}, ... }            // sun,mon,tue,wed,thu,fri,sat
part = { id: "sun-0", title: "...", lines: ["...", "..."] }  // 1-3 חלקים ליום, ≤5 שורות לחלק
```

- כל טקסט בתוך ה-JSON באנגלית בלבד. מפתחות ימים תמיד שלוש אותיות קטנות — לא `Sunday`.
- **שבוע 1 מלא**: כל יום אימון עם אימון אמיתי, לא `{}`.
- שבועות 2-4 חייבים `theme`, `phase`, `summaryLine` ו-`overview` לשבעת הימים; `days`
  יכולים להיות ריקים למילוי מאוחר.

### יום מנוחה — סימון אחד, קשיח

`overview.focus` הוא בדיוק המחרוזת `"Rest"`, ו-`parts` הם `[]` או חלק בודד
`{ title: "REST DAY", lines: ["Rest"] }`. אין ואריאציה ואין ניסוח חופשי — יום מנוחה
מזוהה בתנאי אחד.

### שבוע הדאוליד — אנחנו קובעים, לא המאמן

השדה הוא `phase` ברמת השבוע. אנחנו שולחים את המקום, המאמן מסמן. לבנה מכילה דאוליד אחד
או אפס, והמאמן **לא יוסיף שבוע חמישי בשום מצב**. הקדנציה נספרת אצלנו **מהדאוליד האחרון
שקרה בפועל**, לא מתחילת הלבנה — אחרת נוצרים שני שבועות מנוחה צמודים (זה קרה, 2026-09-03).

### כשהמאמן נכשל

כישלון או סירוב מוצהר = חזרה ריקה עם סיבה מפורשת, ומקבלים אותה כמו שהיא בלי להשלים כלום.
`BLOCK_JSON` חלקי או קטוע = **ניסיון מחדש** — לא להשלים שבוע חסר בעצמנו ולא לשמור לבנה
חלקית כאילו היא שלמה. זה POL קשיח, לא שיקול דעת.

### הכרעת ההגבלה

מגבלה תנועתית מנצחת תמיד — גם מול סקיל מסומן וגם מול ציוד קיים. בפלט: התנועה האסורה לא
מופיעה באף שורה (לא כאלטרנטיבה, לא בסוגריים, לא בבלוק התאמות); החלופה נכתבת כפקודה יחידה;
למתאמן יחיד אין בלוק התאמות, לכיתה יש בלוק אחד בסוף של 2-3 שורות. השורה
`AVOID OVERRIDES THESE MARKED SKILLS` **נשארת ומוצגת** — היא ההוכחה בעין שההגבלה ניצחה,
במקום להסיק זאת מהיעדר תנועה.

## מה אנחנו שולחים

### `blockHandoff` — טקסט מרונדר, לא JSON

שדה ברמה העליונה של גוף הבקשה ל-`generate_block`. השרת מזריק אותו כ-`PRIOR BRICK HANDOFF`
ו**חותך ב-12,000 תווים** (`api/personal-coach.js`) — לכן אנחנו שולחים **מתחת ל-4,000**.
טקסט ולא JSON: המודל קורא טקסט, ו-JSON היה עובר `stringify` וממילא מגיע כטקסט — רק עם
מרכאות וסוגריים שעולים טוקנים בלי להוסיף משמעות.

```
PRIOR BLOCK 2 (absolute weeks 5-8) · deload was week 3 of that block
W1 build · <theme> · <summary>
W2 build · <theme> · <summary>
W3 deload · <theme> · <summary>
W4 build · <theme> · <summary>
PROGRESSED: sun couplet -> triplet | thu AMRAP -> intervals
FORMATS USED: EMOM, AMRAP, chipper, intervals
STANDING REQUESTS: no running for two weeks (knee) | wants more olympic lifting
```

תקרות: כל שורה ≤ 200 תווים; שורת שבוע אחת לכל שבוע של הלבנה שהסתיימה; `PROGRESSED` עד 7
ימים; `FORMATS USED` עד 10; `STANDING REQUESTS` עד 6. כשאין לבנה קודמת — **השדה לא נשלח
כלל**, ולא נשלחת שורה ריקה.

**שלוש הבהרות שמוח המאמן הוסיף, ושתי הראשונות מחייבות אותנו בקוד:**

1. `FORMATS USED` היא **שורה קריטית לסטודיו**, לא נספח. אצל חדר הפורמטים הם ציר
   ההתקדמות (POL-029), ובלעדיה המאמן לא יודע ממה להתרחק.
2. `PROGRESSED` לסטודיו **לא בקילוגרמים** — היא מבנה: `sun couplet -> triplet`,
   `thu AMRAP -> intervals`. ו**אסור לשלוח אותה ריקה** רק כי משקלים לא זזו: שורה ריקה
   נקראת "שום דבר לא התקדם", וזה בדיוק מה שהחוק אוסר.
3. `STANDING REQUESTS` — רק בקשות שעוד בתוקף, ו**אסור להשמיט בקשה שעוד תקפה** כדי לחסוך
   שורה: השכבה אומרת במפורש שבקשה לא פגה עם הלבנה, ולכן היעלמות שלה מהשורה נקראת ביטול.

### `blockStartWeek` — גם בגוף הבקשה וגם כשורה גלויה בחבילה

מספר שלם ≥ 1, אבסולוטי: לבנה ראשונה 1, שנייה 5, שלישית 9. **שניהם, ולא אחד:**

- **בגוף הבקשה** — הנתב של מוח המאמן קורא אותו משם, וזה מה שמדליק את שכבת ההמשך.
- **כשורה גלויה בחבילה** — בבנייה שהאדמין מפעיל בעצמו אין `blockHandoff`, ואז שורת
  החבילה היא האות היחיד שזו לא לבנה ראשונה. בלעדיה: אותה חבילה, אותן שכבות, ואפס סיבה
  למודל לעשות משהו אחר — בדיוק המקרה שהחוק החדש בא למנוע.

הניסוח:

```
BLOCK 3 (absolute weeks 9-12) · deload week 2 of this block
BLOCK 1 (absolute weeks 1-4) · no deload in this block
```

## עלות

`lib/coach-cost-caps.js`: `BRICK_FILL_UNITS = 8` יחידות ללבנה, `MONTHLY_CAP = 40` — כלומר
**חמש לבנות בחודש** ואז חסימה קשיחה בקוד. `DAILY_CAP = 2` עריכות ביום.
`LARGE_REBUILD_WINDOW_DAYS = 7`. Soft upgrade אחד ללבנה. הרחבת קיבולת נעשית במדיניות,
**לא בהרפיית השער**.

## חוב תצוגה שנפתח עם החוזה הזה

POL-029 ("הלקוח נשאר ומשתפר") מחייב שכל לבנה תשמות בנושא שלה מה התקדם מהקודמת — כלומר
`theme` ו-`summaryLine` יישאו מעתה אמירה על התקדמות. **אצלנו זה לא ייראה בעין היום:**
`lib/pprog-display.js` משתמש ב-`theme` רק כתווית קצרה (`phaseShort` — שתי מילים, עד 14
תווים) ולזיהוי דאוליד, ו-`summaryLine` נוסע בחבילה ללקוח (`WEEK_OUT`) אבל **לא מוצג
בשום מקום**. אין מה לתקן ב-22.0 — לבנות שנכתבות ביד לא נושאות את השדות האלה — אבל
**להציג את `summaryLine` בכותרת הלבנה/השבוע הוא חלק מהחיבור ב-22.1**, אחרת ההתקדמות
נכתבת ולא נראית.

## מה נשאר להחליט אצלנו

לשלוח את `blockStartWeek` לחבילה ולגוף הבקשה — ממתין ל-22.1 יחד עם המסלול עצמו. הפריט
היחיד שנדחה במכוון: כל שינוי בחבילה הוא שינוי במה שהמאמן קורא, וזה מקומו בגרסה שיש לה
סבב בדיקות משלה, לא בעלייה של 22.0.
