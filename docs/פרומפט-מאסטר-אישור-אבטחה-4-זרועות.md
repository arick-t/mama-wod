# פרומפט מאסטר לאישור שינויי אבטחה — 4 זרועות

תאריך: 2026-08-06  
מטרה: לאשר שינויי אבטחה לפני מימוש בבראנץ׳, בדיקות, ואז שחרור גרסה מאובטחת יותר.

הזרועות שצריכות לאשר:
1. אבטחת מידע (Security)
2. מח המאמן (Personal Coach Brain)
3. תקציב (Budget / Cost Guardrails)
4. דשבורד אדמין (Founder Admin)

העתק את הפרומפט למטה ושלח לכל מנוע רלוונטי.

---

```text
================================================================================
MASTER PROMPT — DUCK-WOD SECURITY HARDENING APPROVAL (MULTI-ENGINE REVIEW)
================================================================================

You are one of the product governance engines for DUCK-WOD (mama-wod).
We are preparing a security upgrade BEFORE implementation.

Process:
1) You review the proposed changes below.
2) You return a structured approval response for YOUR engine only.
3) After all engines approve (or request edits), we implement on a feature branch,
   test, then release a more secure version.

Important product laws (non-negotiable):
- Workout programming quality must NEVER be compromised (POL-020 / workspace quality law).
- Do not introduce stub/offline/template workouts.
- Do not route generate_*/revise_* through weaker backup models.
- Do not strip programming policy / capability profiling just to save cost.
- Live athlete flows must not break.
- Founder Admin is currently experimental and single-user (founder only), but still must be hardened.

Current context:
- App repo is public (arick-t/mama-wod).
- Personal Coach exists in production.
- Admin dashboard is additive/experimental; athlete data mostly on-device (localStorage).
- Growth model depends on sharing the official app link with friends (must remain allowed).
- We live on Git + Vercel; prefer solutions that stay in this stack.

--------------------------------------------------------------------------------
PROPOSED CHANGE PACKAGE (WHAT WE WANT TO DO)
--------------------------------------------------------------------------------

A) ADMIN ACCESS HARDENING (keep founder's password, remove public exposure)
Goal:
- Keep the same founder password the founder already uses.
- Stop storing that password in public Git source code.
- Stay within Git/Vercel workflow.

Proposed implementation:
1. Move ADMIN password to server environment variable (ADMIN_PASSWORD on Vercel).
2. Remove hardcoded bootstrap password from code.
3. If ADMIN_PASSWORD is missing: admin APIs return closed/unavailable (no weak default).
4. Stop accepting password via URL query params (links/logs leak risk).
5. Keep admin usable for the single founder user.

B) EXTERNAL ACCESS TIGHTENING (without hurting viral link sharing)
Goal:
- Friends can still open the official app link and build plans.
- Reduce uncontrolled backend access from foreign websites/bots.

Proposed implementation:
1. Keep public athlete app usable via official share links.
2. Restrict API CORS from wide-open (*) toward official app domains allowlist.
3. Keep Admin closed to founder only.
4. Keep/strengthen basic rate limits against abuse floods.
5. Explicitly do NOT block legitimate shared-link growth.

C) COACH ANTI-MANIPULATION GUARDRAILS (CRITICAL)
Goal:
- Protect against athletes trying to override the coach AI / extract secrets / bypass rules.
- Make protection enforceable (not prompt-only).

Proposed implementation:
1. BEFORE model call (input firewall):
   - Detect manipulation patterns (ignore previous instructions, reveal system prompt,
     reveal sources/Drive/File Search/warehouse, override hard rules, extract keys).
   - Classify: benign / suspicious / malicious.
   - Malicious => short refusal, stay in coach role, no internals.
   - Suspicious => continue with hardened refusal posture.
2. AFTER model response (output guard):
   - Scan for leakage of sources, system prompt, keys/env, internal policy dumps.
   - If found => replace with safe short refusal and continue coaching.
3. Keep POL-007 + POL-019 as HARD and make them policy-as-code enforceable.
4. Never reduce programming quality for this hardening.

D) SOURCE SECRECY HARDENING ("the brain" remains proprietary)
Goal:
- Prevent direct/indirect source discovery.
- Keep coaching useful while refusing source questions briefly.

Proposed implementation:
1. Uniform short refusal templates (no hints, no partial confirms).
2. Immediate redirect back to useful training help.
3. Deterministic output filter for accidental source-name leakage.
4. Reduce public status/debug fields that expose internal knowledge wiring.

E) ADMIN DATA PRIVACY DIRECTION (PLAN NOW, IMPLEMENT LATER — STAGE 1 FIRST)
Goal:
- Prepare safer admin data architecture without delaying the immediate hardening above.

Direction already agreed for later:
1. Do NOT store athlete coaching data in the public app repo.
2. Use a separate PRIVATE GitHub repo for thin admin snapshots (free, Git-native).
3. Stage 1 only at first: view minimized athlete summary + current block.
4. Stages 2–4 later (change log, admin write-back, AI advisor read-only).
5. Data minimization allowlist; no emails/phones/full chats/medical detail/source names.

NOTE: Item E is for review/alignment now, but implementation priority is A→D first.

--------------------------------------------------------------------------------
ENGINE-SPECIFIC REVIEW FOCUS
--------------------------------------------------------------------------------

If you are COACH BRAIN engine, focus on:
- Conflicts with POL-* (especially POL-007, POL-019, POL-020, POL-021, cost policies)
- Exact policy wording needed
- Athlete-facing refusal templates
- Whether input/output guards can reduce coaching quality
- Any required edits before YES

If you are BUDGET engine, focus on:
- Token/cost impact of input firewall + output scanning
- Extra model calls risk (must avoid dual-path billing)
- Whether guards should be local/deterministic first (preferred) vs extra LLM calls
- Interaction with POL-COST daily/monthly caps
- Cheapest safe design that still hardens security

If you are ADMIN DASHBOARD engine, focus on:
- Founder single-user usability after password move to env
- Risk of locking founder out
- CORS/rate-limit impact on admin.html workflows
- Compatibility with current experimental admin features
- Readiness comments on private-repo Stage 1 later (no need to build it yet)

If you are SECURITY engine, focus on:
- Residual risk after A–D
- Ordering of implementation
- Any missing non-negotiable control before release

--------------------------------------------------------------------------------
REQUIRED RESPONSE FORMAT (EACH ENGINE MUST ANSWER ALL SECTIONS)
--------------------------------------------------------------------------------

1) Engine identity:
- Which engine are you? (Coach Brain / Budget / Admin Dashboard / Security)

2) Verdict for this package:
- YES
- YES-WITH-CHANGES
- NO

3) What you approve as-is:
- Bullet list

4) Required changes before implementation (if any):
- Bullet list with exact recommended wording/behavior

5) Objections / blockers:
- Bullet list (or "None")
- Mark each: HARD blocker / SOFT preference

6) Risks you foresee in your domain:
- Bullet list with severity: Critical / High / Medium / Low

7) Implementation constraints from your engine:
- What must remain true after the change

8) Suggested rollout order from your perspective:
- Numbered steps

9) Test checklist you require before release:
- Bullet list of concrete checks

10) Final one-line recommendation to founder:
- One clear sentence in Hebrew if possible

--------------------------------------------------------------------------------
DECISION RULE
--------------------------------------------------------------------------------

We will implement only after collecting responses from:
1) Security
2) Coach Brain
3) Budget
4) Admin Dashboard

Then we refine the plan, open/continue a feature branch, test, and release a more secure version.

Do not implement code in this response.
Only review and return the structured approval format above.
================================================================================
```
